## القواعد التي لا تُكسر

1. **الطلب ≠ العرض ≠ المهمة ≠ الدفع.** اكتمال المهمة (`COMPLETED`) لا يعني الدفع (`PAID`).
2. **لا يُكتب `status` مباشرة.** كل تغيير يمر عبر `transition()` داخل معاملة قاعدة بيانات واحدة مع سجل حدث وتدقيق.
3. **الخادم يحسب كل المبالغ.** لا يوجد حقل `total` في أي طلب وارد.
4. **التفويض = صلاحية + ملكية + حالة حالية.** غير المالك يتلقى 404 لا 403.
5. **الدفع الإلكتروني لا يُعتمد إلا من webhook موقّع.** عودة المتصفح ليست إثباتًا.
6. **العنوان الكامل ورقم العميل مخفيان عن المهندس حتى `CONFIRMED`.**
7. **عرض السعر المقبول لا يُعدَّل.** العمل الإضافي = عرض إضافي مرتبط به.
8. **المهندس ليس دورًا جديدًا عند وجود متجر:** `hasShop` علامة وليست دورًا.
9. **الواجهة لا تعرض رموزًا برمجية.** الخادم يرسل رموزًا ثابتة، والواجهة تترجمها (انظر `10-frontend-contract.md`).

## التشغيل

```bash
npm install
npm run typecheck      # TypeScript
npm test               # 51 اختبارًا
npm run prisma:validate
npm run openapi:lint
```

> ملاحظة: `prisma validate` الرسمي يحتاج تحميل محرّكات من الإنترنت؛ السكربت `scripts/validate-prisma.mjs` يتحقق من المخطط عبر حزمة WASM الرسمية دون ذلك. في مشروعك الفعلي استخدم `npx prisma validate` و`prisma migrate dev` كالمعتاد.

## كيف تستخدمه في المشروع الفعلي

انسخ `src/domain/` إلى `src/modules/*/domain/` في مشروع NestJS (أو أبقِه حزمة مشتركة)، واجعل كل خدمة تطبيقية تستدعي `authorize()` ثم `transition()` ثم تحفظ داخل `prisma.$transaction`. الكود هنا نقي عمدًا (بلا قاعدة بيانات ولا إطار عمل) ليُختبر بسرعة ويبقى مصدر الحقيقة للقواعد.
